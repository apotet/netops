# NetOps — журнал технических и продуктовых решений

> **Статус:** рабочий журнал принятых договорённостей. Начат 12.11.2026.
> **Назначение:** сохранять контекст между чатами и исполнителями (Grok, Codex, ChatGPT), предотвращать повторные решения и случайные регрессии.
> **Приоритет источников:** работающий код и тесты → этот журнал (объясняет намерения) → roadmap и задачи → устные обсуждения. При противоречии **остановиться и уточнить решение**, а не молча переписать реализацию.
> **Правило обновления:** фиксировать только значимые решения, их причину, область действия, ограничения и ссылки на задачи/PR. Историю не стирать; устаревшие записи помечать «заменено» с новой ссылкой.

## D-001. Заказчик оценивает продукт, а не проверяет исходный код
**Дата:** 2026-11-12 · **Статус:** принято

- Владелец продукта описывает задачи, реальные инженерные кейсы, желаемый результат и оценивает поведение/удобство готового сайта.
- Исполнитель разработки сам проводит code review, тестирование, проверку связей между модулями и исправление ошибок; **не перекладывает проверку diff, SHA, регрессий и сборки на владельца**.
- Отчёты должны различать: «код изменён», «тест прошёл», «PR слит», «GitHub Pages опубликован», «UI проверен вручную». Никаких фиктивных PASS.
- Переключение владельца между темами (например, CLI → расширение банка) **не означает отмену прежних технических решений** и не обязывает его пересказывать их заново.

## D-002. При смене исполнителя сначала восстанавливать контекст
**Дата:** 2026-11-12 · **Статус:** принято

Перед новой реализацией:
1. Прочитать этот журнал, связанные roadmap/issue/PR и существующие модули/тесты.
2. Проверить, не реализована ли функция частично или полностью другими исполнителями.
3. Сопоставить изменения с зависимыми разделами: экзамены, банк, объяснения «Смысл / По делу», база знаний, практика, CLI.
4. Сохранять совместимость и известные контрактные ограничения; изменять архитектуру только осознанно, с отдельной записью причины.
5. После изменений обновлять журнал только если принято новое долговременное решение; не путать факты с предложениями.

**Роли по текущему рабочему распределению:** владелец — постановка и продуктовая приёмка; Grok часто ведёт расширение банка и новые режимы; Codex — точечные технические задачи; ChatGPT — интеграция, проверка и согласованность. Это **не** ограничение прав исполнителей или формальная история авторства каждого коммита.

## D-003. Staging и production строго разделены
**Дата:** 2026-11-12 · **Статус:** принято

- Staging: `apotet/my-gemini-mirror-site` → `https://apotet.github.io/my-gemini-mirror-site/`.
- Production: `apotet/netops` → `https://apotet.github.io/netops/`.
- Исправления, согласованные для staging, можно самостоятельно проверить и слить после реальной приёмки. **Production не публиковать без явного указания владельца.**
- Слияние PR ≠ успешный CI ≠ завершённый Deploy ≠ ручная проверка интерфейса. Указывать отдельные статусы.
- Не «лечить» красный CI предположениями: находить точный падающий тест, держать независимые исправления в узких PR.

## D-004. Банк вопросов и режимы сложности: не ломать логику Grok
**Дата:** 2026-11-12 · **Статус:** зафиксировано текущее поведение, не финальная спецификация будущих режимов

- В коде `src/data/questionsData.ts` общий банк составляется из `questions.json`, `questionsExtra`, `questionsExtraDifficulty`.
- Текущий фильтр `filterExamDifficulty` для уровня `beginner` выбирает `q.difficulty === 'beginner'`; вариант `mixed` допускает вопросы разных уровней. У смешанного экзамена на 10 вопросов отдельная логика квот в `src/data/mixedExam.ts`.
- Новые вопросы повышенной сложности уже добавлены для **будущих режимов**; владелец подтвердил, что сейчас они могут встречаться в смешанном экзамене, но не в «Базе». Не менять эту семантику самовольно.
- Отдельная `База знаний` — каталог уроков, **не** банк экзаменационных вопросов.
- Тесты не должны запрещать легитимное расширение банка жёстко зафиксированным общим количеством, но должны выявлять дубликаты, ошибки структуры и регрессии отбора.
- До изменения доступа к сложным вопросам **согласовать намерение новых режимов** и проверить реальные фильтры; не объявлять существующее поведение багом без оснований.
- Связанный открытый на дату записи PR: [#93 — тест размера банка](https://github.com/apotet/my-gemini-mirror-site/pull/93). **Не считать принятым**, пока CI не станет зелёным и причина оставшегося FAIL не установлена.

## D-005. Обучение CLI: от подсказок к самостоятельной диагностике
**Дата:** 2026-11-12 · **Статус:** принято, реализуется поэтапно

- CLI должен учить реалистичным режимам Cisco IOS, синтаксису `?`, TAB, `show`, сохранению running-config → startup-config.
- В Learn допустима **подсказка алгоритма диагностики**, но нельзя раскрывать точный неисправный порт, готовую команду ремонта или ответ. В Drill/Task тем более.
- Цель проверяется **состоянием сети**, а не совпадением текста введённых команд. Не выдавать модельную L2-связность за настоящий ICMP/ping.
- Не разрушать существующий trunk allowed list: на действующей сети `switchport trunk allowed vlan 310` заменяет список; для добавления нужна форма `switchport trunk allowed vlan add 310`, когда команда и платформа это поддерживают.
- Принятые staging PR: [#89 — аргументная грамматика](https://github.com/apotet/my-gemini-mirror-site/pull/89), [#90 — ссылка урока режимов](https://github.com/apotet/my-gemini-mirror-site/pull/90), [#92 — диагностика show/TAB/?](https://github.com/apotet/my-gemini-mirror-site/pull/92).
- Запланирован реальный кейс с VLAN 310 через десять коммутаторов и сохранением работающих VLAN — [issue #87](https://github.com/apotet/my-gemini-mirror-site/issues/87). **Это backlog, не реализованный стенд**. Юмористическое «УВОЛЕН НАХУЙ!» допустимо только в специально игровом сценарии по договорённости.

## D-006. «Справочник CLI» — ограниченный раздел внутри базы знаний
**Дата:** 2026-11-12 · **Статус:** принято, код слит в staging

- Название: **«Справочник CLI»**, пока без глобального «Словаря сетевика». Переименование возможно по UX-обратной связи владельца.
- Размещение: `База знаний` → `Уроки / Справочник CLI`; не добавлять отдельную глобальную вкладку без нового решения.
- Определения и кликабельные термины уроков используют **один** `src/data/glossary.ts`. Не создавать второй словарь с конкурирующими текстами.
- На текущем этапе отображаются только термины CLI-уроков, с поиском и переходами к связанным урокам; расширение на другие области — отдельное решение.
- Связанные staging PR: [#86 — определения CLI](https://github.com/apotet/my-gemini-mirror-site/pull/86), [#91 — интерфейс справочника](https://github.com/apotet/my-gemini-mirror-site/pull/91).

## Как добавлять решение

```md
## D-XXX. Короткое название
**Дата:** YYYY-MM-DD · **Статус:** предложено / принято / заменено

- **Контекст:** какую проблему решаем.
- **Решение:** наблюдаемое правило/контракт.
- **Почему:** причина и компромиссы.
- **Границы:** что сознательно не меняем.
- **Связи:** issue, PR, тесты, файлы.
```

**Важно:** этот файл фиксирует решения, но не доказывает работоспособность изменений. За фактами — к тестам, содержимому коммитов и фактическому состоянию деплоя.
